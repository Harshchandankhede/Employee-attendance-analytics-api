# REVIEW.md

Defects found in the starter `app/main.py`. "Starter line" refers to the line in
the original file; the fixes are in the rewritten `app/main.py`.

| # | Where (function / line) | What is wrong | How you'd notice it | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` (33-37) | `return minutes if minutes > 10 else 0` compares *whole* minutes, so a punch-in 10:00.001 late rounds to 10 and is not counted. R2 says late when strictly more than 10 **minutes and seconds** have passed, and `10:15:59` must give 45. | R2's own examples: shift 09:30, punch-in 09:40:01 should be 10 minutes late, the starter returns 0. | Compare elapsed seconds against the 600-second grace, then floor the minutes: `if seconds > 600: return seconds // 60`. Verified against all three contract examples. |
| 2 | `compute_late_minutes` (35) | Builds the shift start with `punch_in.replace(hour=h, minute=m)`, which keeps the *UTC* wall clock but is compared against a shift time that is **IST**. A 09:30 IST punch-in is 04:00 UTC, so lateness was computed five and a half hours out. | Punch in on time and the API reports ~330 minutes late. | Compare real instants: build the shift start as an IST wall-clock time (`ist_moment`) and subtract. |
| 3 | `compute_overtime` (44-47) | `max(0, minutes past shift_end)` counts any overtime at all. R3 only counts it at 30 minutes or more. | Sample document 1 punches out 18:35 against an 18:30 shift end and the starter stores `overtime_minutes: 5`. The sample itself says it should be 0. | Return the minutes only when at least 1800 seconds have passed, otherwise 0. |
| 4 | `compute_overtime` (46) | `datetime.fromisoformat(date_str)` produces a **naive** datetime and tags it `tzinfo=IST`, so an overnight shift's end lands on the wrong calendar day. EMP0005 (22:00-06:00) would get its end at 06:00 on the same day, before the shift began, producing negative overtime. | Punch out at 06:40 after a 22:00 shift: overtime is 0 or negative instead of 40. | Derive the end instant from `shift_bounds`, which adds a day when `shift_end <= shift_start`. |
| 5 | `compute_work_hours` (40-41) | Uses Python's `round()`, which is banker's rounding and works on binary floats. R4 requires half-up: `2.675` becomes `2.67`, and `round(2.5)` is `2`, not `3`. | Compare against R4's definition; `2.675` must be `2.68`. | A single `round_half_up` helper using `Decimal` with `ROUND_HALF_UP`. Also used for every reported number (R8). |
| 6 | Derived fields | `half_day` (R5) is never computed anywhere. Every punch-out stores `False`. | Any day shorter than 4.50 hours is stored as a full day, so `present_days` is over-counted. | Added `compute_half_day`, applied on punch-out and after every correction. |
| 7 | `health` (72-74) | Returns `{"status": "ok"}` without touching MongoDB. | Stop `mongod`; `/health` still returns 200 and the runner believes the service is ready. | `db.command("ping")`, raising 503 when it fails. |
| 8 | `list_employees` (93) | `skip = page * page_size`, but `page` starts at 1 (R10). Page 1 skips the first `page_size` records. | `GET /employees?page=1&page_size=3` on the sample returns EMP0004-EMP0006, hiding EMP0001-EMP0003. | `skip = (page - 1) * page_size`. |
| 9 | `list_employees` (94) | `total = db.employees.count_documents({})` ignores the `department` filter. | `GET /employees?department=Support` returns `total: 6` while showing 2 items. | `count_documents(q)` with the same filter. |
| 10 | `list_employees` (95) | No sort, so employees come back in natural storage order. The contract requires `emp_code` ascending. | The response order changes as documents are inserted or updated. | `.sort("emp_code", ASCENDING)`. |
| 11 | `list_employees` (89-91) | No bounds on `page_size`, and no `422` for `page < 1`. R10 caps `page_size` at 100. | `page_size=100000` is accepted and tries to serialise the whole collection. | `Query(ge=1, le=100)` and `Query(ge=1)` on `page`. |
| 12 | `create_employee` (79-83) | Uniqueness is enforced by a read-then-write check, so two simultaneous creates can both pass it. The contract requires a **database unique index**. | Two parallel POSTs with the same `emp_code` both return 201 and two employees are stored. | A unique index on `emp_code` created at startup; the `DuplicateKeyError` becomes 409. The pre-check remains only for a friendlier message. |
| 13 | `create_employee` (53-60) | No validation at all: `emp_code` pattern, email format, `joined_on` format, and the rule that `shift_start` must differ from `shift_end`. | `POST /employees` with `shift_start == shift_end` succeeds. | Patterns and lengths on the Pydantic model; the shift comparison is a business rule, so it is an explicit 422 in the endpoint. |
| 14 | `create_employee` (82) | `created_at = datetime.now()` is naive and local. The contract wants an epoch-millisecond instant. | The response contains a local time string rather than epoch milliseconds. | `now_utc()` and `dt_to_ms` on the way out. |
| 15 | `punch_in` (102) | `datetime.fromtimestamp(...)` with no timezone produces a naive datetime in the *server's* local zone. Every attendance date then depends on where the process runs. | Run the server in UTC and a 20:00 IST punch-in is filed under the previous day. | `ms_to_dt` returns an aware UTC instant; the date comes from `attendance_date`, which converts to IST first (R1). |
| 16 | `punch_in` (103) | `ts.date()` takes the date in UTC or server-local time. R1 requires the **IST** calendar date, and for an overnight shift a punch-in before `shift_end` belongs to the previous day. | 18 | `punch_in` (113) | No 404 for an unknown employee: `emp["shift_start"]` raises `KeyError`, which surfaces as a **500**. | `POST /attendance/punch-in` with `emp_code: "EMP9999"` returns 500. | Explicit lookup with 404. A 500 is always a failed test. |
| 19 | `punch_in` (102) | Instants are not truncated to whole seconds (R1), so 09:40:00.900 is stored and returned as-is and can change a late calculation. | Punch in at 09:40:00.900 and `late_minutes` disagrees with R2's boundary. | `ms_to_dt` truncates microseconds; the truncated value is what is stored and returned. |
| 20 | `list_attendance` (144-147) | Loads the **whole collection** into memory, sorts it in Python, then slices. | 21 | `list_attendance` (145) | Sorts by `date` descending only. The contract wants `date` descending **then** `emp_code` ascending. | Records sharing a date come back in arbitrary order between requests. | `.sort([("date", DESCENDING), ("emp_code", ASCENDING)])`. |
| 22 | `list_attendance` (134-141) | No `422` when `date_from` is after `date_to`, and no check on an unknown `status`. | `?date_from=2026-07-10&date_to=2026-07-01` returns an empty page instead of 422. | Explicit 422s for both. |
| 23 | `list_attendance` (149), `punch_in` (118-120) | Responses hand BSON values straight to FastAPI, so datetimes serialise as ISO strings and `id` is exposed. The contract wants integer **epoch milliseconds** everywhere, and no id. | Any response containing `created_at` or `punch_in` shows `"2026-07-06T03:58:00"`. | One `record_to_json` / `employee_to_json` pair converts every instant and never exposes `_id`. |
| 24 | `list_attendance` (149) | Adds an `id` to each record. A record is addressed by `(emp_code, date)`; `_id` is internal to MongoDB and must never appear. | The response contains a field the contract does not define. | The serializer emits exactly the contracted fields and nothing else. |
| 25 | Whole file | Naive datetimes come back from PyMongo and are mixed with aware ones, which raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Punch out on a server whose local zone is not UTC. | The client is built with `tz_aware=True`, so every datetime read from MongoDB knows it is UTC. |
| 26 | Legacy records | Seeded documents may omit `history` and `half_day` (sample 9), but both are **required** in the response. | `GET /attendance` for EMP0002 omits the two fields entirely. | The serializer defaults a missing `history` to `[]` and a missing `half_day` to `false`. |
| 27 | Whole file | No indexes are created anywhere, though the brief makes this the application's job. | `explain` on `GET /attendance` shows a `COLLSCAN` over 100k records. | Six indexes created on startup through `lifespan`, idempotent so it is safe against the grader's existing data. |
| 28 | `PunchInIn.status` (66) | Free-text `str`, so any status is accepted, including `ABSENT` and `LEAVE`, which no punch-in may create. | `POST /attendance/punch-in {"status": "ABSENT"}` succeeds. | Restricted to the three presence statuses; anything else is a 422. |

## Examined and deliberately not changed

- **`status` default of `PRESENT` on punch-in.** Matches the contract; kept as is.
- **`health` returning only `{"status": "ok"}`.** The schema requires `status` and
  nothing else; adding fields would be inventing contract.
- **`emp_code` as the employee identifier rather than `_id`.** The brief is explicit
  that `_id` is internal and never appears. Kept, and made it a real unique index
  instead of an application-level check.
- **Reading stored `work_hours` / `late_minutes` rather than recomputing them in
  analytics.** DATA_MODEL.md says the stored values are authoritative, so the
  pipelines read them and never recompute from punch times. Recomputation happens
  only where the API itself writes a record.
- **Storing `work_hours` as a double rather than an integer of minutes.** The data
  model specifies a double; seconds are the source of truth and rounding is applied
  once, at the boundary.
